Slow GPU/TPU Training ("Input-Bound" / CPU Preprocessing Starvation)

tf.data + Host vCPUs Watch Invalid 3-GPU Trap!
Exam Symptoms: "GPU/TPU utilization is low (~15%)," "CPU utilization is 100%," "high infeed percentage in Cloud Profiler," "hundreds of millions of BigQuery rows," or "custom image preprocessing on n1-standard-8 + 1 V100."
Root Cause: Your accelerator is starving while waiting on BigQuery/GCS reads or host CPU image decoding/augmentation.
Before vs. After — Fixing Input-Bound & CPU-Starved Accelerators Q#15, Q#28, Q#65, Q#82, Q#126, Q#132 (C), Q#314, Q#338 (C)
Optimization Step Exact Grounded API / Hardware Fix Why It Wins (and Trap Eliminated)
1. Materialize Binary Shards Convert millions of small CSV/JPGs or hundreds of millions of BigQuery rows once into sharded GCS TFRecord files (Q#132 (C) Q#263 (C)) Eliminates per-file GCS metadata overhead and avoids slow BigQuery Storage Read API scans on every training epoch
2. Parallelize Reads & Scale Host vCPUs Dataset.interleave() + map(..., num_parallel_calls=AUTOTUNE), OR upgrade n1-standard-8 to 24 vCPUs + 1 V100 GPU (Q#338 (C)) Eliminates host CPU image-preprocessing starvation without hurting accuracy (Trap: 3 V100 GPUs in Option D is an invalid GCP GPU count—only 1, 2, 4, 8 exist!)
3. Decouple Producer/Consumer Dataset.prefetch(tf.data.AUTOTUNE) (Q#28 Q#126 Q#314) CPU prepares batch N+1 asynchronously while GPU/TPU executes forward/backward pass on batch N

Bucketing/Coarsening vs. Tokenization

For numerical/spatial quasi-identifiers (AGE → quantiles, LATITUDE_LONGITUDE → rounded single precision), coarsen/bucket to achieve k-anonymity while preserving ordinal & spatial ML signal (hashing destroys numeric distance!). Use deterministic tokenization only for exact join keys (customer_id).

Preventing Preprocessing Skew Between Training & Serving

ML Pipelines Zero-Skew Guarantee
Core Principle: Never maintain separate SQL/Python feature-engineering scripts for training vs. serving, and never split numeric scaling into SQL while doing categorical encoding in TensorFlow across multi-epoch BQ scans. Bake the entire transformation graph inside the exported model artifact.

Track A: In BigQuery ML (SQL) Q#4, Q#29, Q#289

Put all feature engineering inside the TRANSFORM(...) clause of CREATE MODEL.

BigQuery ML saves the exact SQL transformations inside the model so ML.PREDICT applies them automatically at serving time.

Track B: Custom TensorFlow at Scale Q#211, Q#263 (C)

Run TFX (ExampleGen → StatisticsGen → Transform) on Cloud Dataflow and materialize sharded TFRecords in GCS.

tf.Transform computes full-pass dataset stats once, eliminates slow per-epoch BigQuery reads, and embeds transform_fn directly inside the exported SavedModel.
